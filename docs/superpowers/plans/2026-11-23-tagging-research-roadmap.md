# 数据打标后续研究与验证方案

**日期：** 2026-11-23初稿；2026-11-24修订双目标、研究范围与总体收益验证顺序。

**状态：** 访谈范围已确认，进入文档与基线准备；本次未执行代码改造或远程实验。

**目标：** 并列评估批量INSERT与标签UPDATE，在正常运行结果正确的条件下，解释各自端到端收益与成本；百万行/秒为探索目标，两条路径允许收益和贡献不对称。

**架构：** 保留 Trino SQL → Pixels INSERT 直写 / UPDATE 增量标签 → 显式 COMPACT → 最终查询的主线。开题前论证问题、方法与实验设计；先建立双路径总体对照，暂缓新增微优化；开题后在鲲鹏平台核验外部方案，再依据证据选择导入处理、共享处理、文件选择或有界批处理。持久化索引重新设计属于独立决策，不能在本方案执行中自行扩大范围。

**技术栈：** Trino 466、Pixels、Java、RocksDB 标签与主键索引、SQLite 主索引、现有 RPC 与显式物化流程。

本文是研究路线和实验决策方案，不是已经批准的逐行实现计划。通过每个实验门槛后，再针对该项形成代码补丁与实现细节。

**阶段边界：** 开题材料需明确外部方案选择、语义差异、指标和公平性设计，不以已经完成Hudi/StarRocks实测为前提。下文运行与性能验收是开题后的研究任务，不是学校的开题资格条件；鲲鹏测试尚未执行。

- 本文性能数字来自仓库实验记录，本次未独立复跑。不同配置、表状态与计时口径之间不直接计算加速比。

已有收益支持继续研究，但尚不足以证明方案相对外部方案的完整周期优势：

## 2. 研究问题与贡献候选

论文并列研究两个待验证问题：**INSERT直写减少的中间处理是否被转换、索引及发布成本抵消？UPDATE增量记录与延迟物化是否减少完整打标周期成本？** 不强迫两者共用同一算法或形成同等幅度的收益。

### 2.1 直接相关工作与差异要求

| 代表性工作 | 已有机制 | 对本课题的约束 |
| --- | --- | --- |
| [StarRocks列模式部分更新](https://docs.starrocks.io/docs/sql-reference/sql-statements/table_bucket_part_index/UPDATE) | 面向少量列、大量行更新 | 少列打标定位本身不新；实验必须核验实际列模式及条件 |
| [Hudi 1.0 MOR部分更新](https://hudi.apache.org/releases/release-1.0/) | MOR支持部分列更新 | 仅记录修改列、以后合并不能单独作为创新 |
| [Iceberg更新模式](https://iceberg.apache.org/docs/latest/configuration/) | 配置支持COW/MOR，具体行为受引擎约束 | 不把通用格式能力当作Trino 466能力，不只选较弱配置 |
| [Databricks删除向量](https://docs.databricks.com/aws/en/delta/deletion-vectors) | 更新可避免立即重写原Parquet文件 | 不立即重写并非独有；删除向量不等于部分列新值存储 |
| [L-Store](https://arxiv.org/pdf/1601.04084) | 列式增量、lineage与延迟合并 | 延迟列存物化已有学术基础，必须说明方法差异 |

这是代表性直接相关工作的初步核对，不是穷尽最新SOTA的综述，也不是外部性能实测。执行前为各候选记录固定版本、更新表示、读时处理、合并策略、语义和配置，不能从产品名称推断实际执行机制。

学术机制对照统一维护在[当前开题报告](../../thesis-proposal-20261123.md)第2.2—2.7节：
PDT讨论位置增量，L-Store讨论累积与非累积更新，Fast Updates已有值到元组ID列表
的组织，SAP HANA与Mainlining讨论表示转换。因此，共享行集合、只保留最新值或
延后物化均不能仅凭概念作为新颖性主张。执行阶段对应主稿第3.4节的H0—H3，先测
重复处理、覆盖关系和文件触及比例，再选择主要贡献；不要求三个假设同时成立。

### 2.2 贡献候选与信心边界

1. **批量导入的成本削减。** 分析直写与可比旧路径的源读取、转换、文件、索引及发布成本，先证明总体收益，再研究具体处理组织；接通Writer本身不作为创新。
2. **满足依赖条件的重复处理削减。** 验证多列共享与多轮覆盖能减少哪些重复定位、传输或状态处理。现有内存列表复用是工程基础；需要方法差异和消融才能支撑进一步研究主张。
3. **增量处理与低成本物化协同。** 研究有效增量、文件分布和内存约束下的处理组织。按文件选择、有界RPC和并行本身均不作为创新，须证明相对已有方法的差异及成本收益。
4. **适用边界与实证。** 解释列数、轮次、更新依赖及文件触及比例如何改变整体成本。实证贡献不称为新算法。

当前判断是“路线合理，值得有限实验”，不是“已证明有创新或能超过成熟系统”。不承诺百万行/秒。若仅有常规工程优化，应如实定位并与导师确认论文要求；若代表性负载整体无优势，应复审架构。正常运行正确性是实验前提；故障恢复与故障注入不作为本阶段目标或性能门槛，披露持久化配置及已知限制。

## 3. 全局约束与计时契约

- 遵循原始会议：打标期间不要求普通查询立即看到标签，完成物化后验证最终数据。原始会议没有规定只更新少列、固定多轮或必须达到百万行/秒。
- 保留存在性过滤、列隔离、同列覆盖、decimal scale和NULL语义；不通过跳过检查或关闭WAL制造加速。
- 不查询不等于UPDATE之间无依赖。后续谓词或赋值依赖此前标签时，必须保持逐语句语义；不能只比最终结果或用独立常量负载代表任意SQL。
- INSERT完整批量导入与UPDATE主键筛选、常量赋值、独立多轮打标并列；不扩展首期DELETE，不新增打标期间在线查询协议。
- 非主键筛选、依赖前轮标签和复杂表达式仅核对能力边界，暂不另开优化主线。不得用不支持的语义生成虚假性能结果。
- 部署记录两个仓库SHA、jar校验值、JDK、机器CPU/内存/磁盘、服务参数及其实际生效值。
- 主测例为68列，60个标签列初始SQL NULL；必须检查加载后的值，不能将CSV空串当NULL。独立table root，显式主键 `id`，`pk_scheme=rocksdb`。
- 初始化、进程重启后的运行和稳态重复分别记录；跨候选比较时保持缓存状态规则一致。

报告SQL完成和必要的最终可查询时间；持久化配置另作说明，不强制划分第三个完成时点：

| 指标 | 定义及用途 |
| --- | --- |
| INSERT/UPDATE SQL时间 | 客户端提交至成功响应；另外记录Trino timeline，不与内部计时混用 |
| 打标周期时间 | 从第一次UPDATE提交到最后结果可查询的墙钟时间，包含各轮UPDATE、必要COMPACT及发布；验证查询执行时间单独报告 |
| INSERT及导入加打标时间 | INSERT单独记录发布可见时间；若研究导入加打标工作流再合并计时。预置源表构建单列，表到表源扫描包含在INSERT SQL时间内并另列阶段耗时 |
| 持久化条件（说明项） | 记录WAL、同步写、checkpoint及计时终点；比较要求需要的额外步骤计入，不以故障注入或重启恢复作为门槛 |

分别报告每轮实际匹配行数、累计行更新次数、整个周期去重行数、单元格更新数。吞吐的分子必须写明，例如30轮更新同一批100万行，累计为3000万行更新，但去重仍为100万行。

## 5. 阶段B：验证多列共享的真实收益

**假设：** 同一行集合修改列数增加时，共享主键能减少重复处理；但持久化与物化可能掩盖收益。先结合D0和最小外部对照确认成本，再决定是否制作新原型；统计与现有实现消融可提前进行。

- [ ] 同一基础数据分别更新2、8、60列；每组对照仅切换共享处理实现，保持batch、并行、布局及缓存规则不变。
- [ ] 如需制作关闭共享的实验变体，保留完全相同的SQL语义和存在性过滤；不能用跨多个无关提交的对比代替消融。
- [ ] 记录主键解析次数、RPC字节、对象分配、峰值RSS/堆、RocksDB写入字节、SQL时间与完整周期时间。
- [ ] 对比30轮×2列与1轮×60列，两者最终结果相同，均在全部打标结束后物化；此对照衡量轮次成本。另对同样30条独立赋值语句比较逐轮物化与末尾物化，隔离合并频率影响。不能仅由第一个对照证明延迟合并价值。
- [ ] 检查重复覆盖同列时索引体积与历史版本增长，区分逻辑有效增量和历史记录。

**代码定位：** Trino仓库 `connector/src/main/java/io/pixelsdb/pixels/trino/PixelsMetadata.java`；Pixels仓库 `pixels-index/pixels-index-rocksdb/src/main/java/io/pixelsdb/pixels/index/rocksdb/PixelsTagIndex.java`。

**边界：** 当前内存/RPC共享不等于持久化只存一份主键集合；不能声称已把整个系统存储复杂度降为 O(N+C)。若要持久化共享集合，需要另行讨论引用、版本、回收和恢复机制。

**门槛：** 只有内部耗时下降而SQL、周期、资源均无稳定收益时，停止继续打磨此项；将其记录为局部优化，不作为论文的主要性能结论。

## 6. 阶段C：先验证文件选择，再推进物化内存优化

物化是重点候选，但先做低成本统计及外部对照；根据证据决定是否投入原型，不预设它一定比共享处理更值得做。

### C1. 受影响文件选择

- [ ] 基于现有 `PixelsTagCompactor.TagIndexSnapshot` 的位置集合统计受影响file ID，先仅输出统计，与当前实际重写文件集合比较。
- [ ] 对更新比例1%、10%、100%，分别构造聚集更新和均匀随机更新；记录触及文件数/有效文件总数、输入输出字节和重写时间。
- [ ] 只有存在明显的无关文件重写，才制作按文件选择的原型。同时处理当前ordered/compact输入及各自storage，不假设所有文件同一种存储。
- [ ] 验证未选中文件仍保持可见且不被retire；选中文件内未更新行必须保留；位置索引只更新实际重写行，最终逐键结果与全量合并一致。
- [ ] 第一轮实验可用全新表限定范围；推广至重复周期前，必须解决“历史标签不等于本轮待物化标签”的识别，验证水位/版本及失败重试后再考虑安全回收。

**门槛：** 若更新1%行已触及接近全部文件，则该分布下文件过滤收益有限，应如实报告；不要为制造结果人为改变主测例。若所有代表性分布均无可省文件，停止该原型。

### C2. 有界批处理

- [ ] 对标签快照、待解析批次、主键到行映射、重定位映射分别测量内存随规模增长的曲线。
- [ ] 优先限制在途批次数及字节数，完成一批释放一批，测试慢RPC和异常取消时不会无限积压。
- [ ] 小批次RPC及固定线程池不等于整体内存有界；保留全量快照/映射时，结论只能是降低瞬时积压，不能声称常量内存。
- [ ] 若全量映射成为10M扩展的硬瓶颈，再设计按文件处理或临时落盘；涉及持久化协议、发布原子性改变时单独评审。

**代码定位：**

- `pixels-cli/src/main/java/io/pixelsdb/pixels/cli/executor/PixelsTagCompactor.java`
- `pixels-cli/src/main/java/io/pixelsdb/pixels/cli/executor/CompactExecutor.java`
- 同包对应测试包括 `PixelsTagCompactorSnapshotTest`、`PixelsTagCompactorRelocationTest`、`PixelsTagCompactorRowLocationTest`。

**门槛：** 正常运行正确性不回退，且周期时间或峰值内存/写入字节有可重复改善。收益须超过实测波动，不预设15%或20%的统一门槛；资源改善伴随的时间代价也要报告。

## 7. 外部验证工作线D：开题设计与开题后对照

### D0. 开题前完成设计，开题后与阶段A并行验证

- [ ] 开题前形成StarRocks列模式、Hudi MOR部分更新的机制对照，写清候选版本/接口的选择依据、预期语义差异、评测指标及部署风险。尚未核验的兼容性明确记录，不要求现在完成实测。
- [ ] 开题后在鲲鹏环境核对依赖、版本、接口与支持边界，计划至少跑通一个直接部分更新基线，并验证实际执行路径。说明选择依据，不能因为另一候选更快而排除它。
- [ ] 覆盖2/8/60列、缺键、NULL及独立多轮赋值；加载/upsert接口若会插入缺失键，不能直接当作UPDATE对比。存在性匹配、键集合生成及转换成本计入相应端到端边界，预计算微基准另外标注。
- [ ] 验证当前Trino 466与Iceberg组合支持所需更新方式、类型和结果可见语义；不把通用COW/MOR配置直接当作Connector能力，不把SQL不支持解释为性能差。
- [ ] 在Pixels对应正确性通过后，对1M代表性负载做最小配对比较，按相同硬件和资源预算记录SQL、物化、可见时间与字节量；存储布局/部署差异无法一致时明确披露。

直接部分更新基线回答“是否比已有同类方案有价值”；同Trino的Iceberg对照尽量控制引擎变量；Retina仅作内部基线。三者不能互相替代。跨引擎差距不直接归因于某一算法。

### 目标平台与部署顺序

- 主要实验拟在鲲鹏服务器开展，型号、核数、内存、磁盘、操作系统及节点数按实际配置登记；本方案不预设规格，也不声称已验证所有候选兼容。
- 先核验JDK、RocksDB JNI、项目C++/JNI和存储依赖的编译、加载与运行，再进行小表语义、两周期物化和正常运行读回；外部基线单独验证。
- 核心结果采用同平台、同资源预算、相同逻辑数据与更新任务的配对比较。记录CPU/内存限制、堆、并发、存储和实际生效参数，记录SQL成功和必要的最终可见时间，披露持久化条件。
- 标签测例覆盖NULL、部分/充分填充，以及不同标签值基数；高重复标签上的结果不能代表任意宽表。
- 跨平台复现是可选工作，优先比较各平台内的优化相对收益；不把不同硬件上的绝对吞吐差归因于处理器架构。平台迁移本身不作为创新。
- 兼容性受阻时，记录具体依赖或接口问题，评估其他版本或合适候选并调整计划；不能将无法运行的基线记作性能差，不能用异构硬件直接排名。

### D1. 依据初步成本差异选择优化后，再做规模与边界验证

- [ ] 主比较终点统一为最终结果可查询；Pixels必需的COMPACT计入。对手无需额外OPTIMIZE才能可见时，不强制它执行OPTIMIZE以拉平成本。
- [ ] 另外报告最终查询耗时、后台维护及存储成本；耐久性配置对齐，无法对齐的部分显式披露。
- [ ] 先固定1M正确结果，再扩展10M；100M由内存、时间与设备容量决定，不以1B作为最低交付要求。
- [ ] 采用分层矩阵：2/8/60列，多轮覆盖，聚集/随机/缺键，主键谓词（时间/维度谓词仅作能力核对），1%/10%/100%更新。先单因素筛选，再对影响最大的因素交叉验证，不盲目跑全组合。

**交付：** 完整周期时间、实际更新/去重行吞吐、物理写入字节、峰值内存、查询代价及失败样本；每张图可追溯到SHA、配置、输入与全部原始运行。

**方向决策：** 部分负载获益则明确适用范围；代表性负载在周期、写入量和资源上均无优势，则进入架构复审，不继续用内部最好成绩支撑方向。

## 8. INSERT并列研究线：总体对照后再选择优化

INSERT与UPDATE并列，先完成阶段A的总体对照。优先定位端到端关键路径，不凭局部CPU热点连续追加微优化。

- [ ] 区分源表扫描/数据生成、Writer编码写文件、主键索引写入、元数据发布的时间。
- [ ] 核验参数确实进入grouped-primary实际写入路径；此前无效的flush并行参数不能继续作为有效自变量。
- [ ] 只对剖析显示占比最大的阶段做一个变量的实验，保持WAL和SQL语义；保留无收益实验记录。

INSERT独立判断收益，不因其在某次打标周期中占比较低而降为辅助工作；两条路径允许贡献不对称。

## 9. 建议执行顺序与收敛条件

以下区分开题准备与开题后工作包，不替代学院要求，也不假设学校提交日期。实施周次以开题通过和相应实验资源可用为前提。

| 工作包 | 输出 | 后续决策 |
| --- | --- | --- |
| 开题准备 | 问题与相关工作对照、具体方法假设、鲲鹏实验设计、候选基线选择及风险、已有原型证据 | 论证价值与可行性，不要求完成外部实测或证明最终创新 |
| 首批验证：阶段A双路径总体对照 | 版本与输入固定、正常运行正确性、INSERT/UPDATE配对及成本解释 | 可比性不成立先补适配；总体收益不明暂缓新增微优化 |
| 开题后目标平台与D0运行验证 | 鲲鹏依赖、小表验证及至少一个可比外部方案 | 同平台比较；不将未完成实测作为开题门槛 |
| 第二批：D0最小配对比较 + B消融 + C1统计 | 外部成本差异、多列消融、文件触及比例 | 根据证据选定一个改造项，不预设路线胜出 |
| 第三批：选定的共享处理/文件选择/有界批处理原型 | 有机制解释和对照的优化 | 无收益则停止该项，保留负结果 |
| 第四批：D1规模与边界 | 1M/10M对照、适用边界与复现包 | 固化论文贡献，必要时提交架构复审 |

开题前优先完善“研究问题—拟议方法—实验验证”的对应关系及平台可行性计划。开题后、鲲鹏资源可用的首个约10个工作日优先推进依赖部署、小表验收、fixture与计时固化，并启动外部基线兼容性验证；规模化性能对照随后开展。这是条件性的工作量估计，不承诺届时全部通过。平台迁移遇到阻碍时调整排期，不把开题后验收倒置成开题前要求。

以下事项必须先讨论，不在本方案中默认授权：替换标签索引主组织、改为持久化共享主键集合、引入永久稳定row ID、改成逐文件delta体系、增加在线读合并或新的分布式提交协议。
