## 一、课题名称

面向大规模数据打标的云原生列存引擎 SQL 行级更新机制研究与实现

英文题目（参考）：Research and Implementation of SQL Row-level Update
Mechanism for Large-scale Data Tagging on a Cloud-native Columnar Engine

## 二、研究背景与意义

### 2.1 业务背景

在机器学习特征工程、数据治理和数据资产管理等场景中，需要对存量大规模
数据集进行增量式“打标”：通过 SQL 的 INSERT、UPDATE 语句，为大量数据行
的标签列赋值，并在全部打标完成后统一进行数据比对与下游消费。该类负载
的明确约束是：支持大量行的标签列增量赋值，打标期间不查询数据，全部
打标完成后进行比对，对严格在线 ACID 的要求宽松。每次更新列数、打标
轮数和更新行分布尚未由会议量化，应作为实验变量；不能将当前两列更新
测例直接推广为业务只更新少数列的前提。宽松事务要求也不免除最终结果
正确、失败可处理和已提交数据可恢复的责任。

本课题依托的 Pixels 是一套云原生无服务器（serverless）OLAP 引擎，
通过 Trino 对外提供 SQL 接口，底层采用列存文件组织，并由 Retina 组件
基于 MVCC 日志提供变更回放能力。现有 Retina 接口面向整行回放设计，在
标签更新场景下，整行回放可能把未修改列一并处理，造成数据膨胀和写放大。
这一问题由会议提出，具体放大程度及其随更新列数的变化需要对照实验量化。
同时，Pixels 底层存储不支持原地更新，存储侧接口复杂，直接改写数据文件代价
高昂。

### 2.2 问题提出

在不改造底层存储格式、不要求严格在线事务的前提下，如何让一个面向分析
负载设计的列存引擎具备高吞吐的 SQL 行级 INSERT/UPDATE 能力，并保证
打标结果在异步合并、进程重启之后仍然正确可见，是本课题要解决的核心
问题。具体可分解为：

1. 如何在 Trino Connector 的 SPI 框架内承接 INSERT/UPDATE 语义，将
   候选主键域转化为实际匹配集合，并为不能下推的业务谓词提供正确路径；
2. 如何在不原地改写列存文件的情况下，持久化记录“标签值到主键集合”的
   映射，并支持多标签列、多种数据类型的正确共存；
3. 如何通过异步 Compaction 将索引变更物化为新的列存文件，同时维护主索引
   与标签索引的一致性；
4. 如何在组件重启、检查点重发等异常场景下保证已提交数据不丢失、不重复、
   可恢复；
5. 如何刻画并消除百万行以上规模的性能瓶颈，使系统具备向千万、亿级扩展
   的工程基础。

### 2.3 研究意义

理论层面，本课题是“写入路径与物化路径分离”思想在云原生列存引擎上的
一次完整工程实践：以独立索引承接高频行级变更、以异步合并收敛物理布局，
与主流湖仓表格式的行级变更技术处于同一技术谱系，可为列存系统支持行级
DML 提供设计参照和量化评测依据。

工程层面，课题成果直接支撑业务打标流程，使数据工作者可以使用标准 SQL
完成百万级标签赋值，而无需依赖专用回放接口；其中关于 vnode 索引冷启动、
服务端分组写入、Compaction 重复解析等问题的定位与优化，对 Pixels 主干
的 DML 能力建设具有回馈价值。

## 三、国内外研究现状

### 3.1 列存系统的行级变更

基于不可变列式文件的分析系统通常通过增量记录或文件重写实现行级变更。
LSM-Tree
（Log-Structured Merge-Tree）通过将随机写转化为顺序写、后台合并 SSTable
来支撑高频更新，是写读分离架构的经典基础，但其合并会引入写放大。
分析型引擎在引入行级变更时，普遍采用“基线文件 + 增量变更 + 异步合并”
的组织方式，本课题的 Tag Index 与 Compaction 设计遵循同一思路。

### 3.2 湖仓表格式的行级变更机制

近年出现的开放湖仓表格式围绕行级 INSERT/UPDATE/DELETE 形成了代表性
方案：

- Apache Hudi 采用 Copy-on-Write 与 Merge-on-Read 两种表类型，配合记录级
  索引（record-level index）支撑快速 upsert，写入与合并在时间上解耦；
- Apache Iceberg 通过 position delete 与 equality delete 文件描述行级
  删除与变更，读时合并，后台 compaction 负责收敛；
- Delta Lake 引入 deletion vector 以位图方式标记被删除/变更行，降低小
  文件数量与读时合并成本；
- Apache Paimon 面向流式更新构建主键表，底层采用 LSM 结构与多级
  compaction，支撑高吞吐 changelog 写入。

这些系统展示了记录增量、同步重写和延后合并等不同权衡；其写入路径可能
持久化增量行、删除标记及索引，不能一概归纳为只记录行/键映射。
Hudi Merge-on-Read 的 snapshot 查询可合并基础文件与增量日志读取最新
结果，read-optimized 查询则依赖已合并基础文件。本课题当前普通扫描需要
Compaction 才能读取新标签，因此对比时须明确查询可见性和维护成本。
本课题将标签变更托管在独立 RocksDB 索引服务中，通过 gRPC 与 Trino
交互，并与 Pixels 主索引、元数据及 Retina 可见性机制协同。这是需要
评测的设计取舍，尚不构成优于上述系统或具有算法新颖性的证明。

### 3.3 查询引擎写能力与嵌入式索引

Trino（前身 Presto）以交互式联邦查询见长，其 Connector SPI 长期以读
为主，写接口的工程实现需要自行处理页汇聚、文件提交与元数据发布。
RocksDB 作为高性能嵌入式有序 KV 存储，被广泛用于需要持久化键值映射的
系统组件中，适合承接标签值到主键集合的追加式写入与点查，但在多列命名
空间、批量请求体积、列族（column family）初始化调度等方面需要针对性
设计。

### 3.4 现状评述

本课题以 Pixels 的具体存储与业务约束为研究对象，检验独立标签增量记录
在不同更新列数、更新范围和打标轮数下，能否降低完整打标周期的写放大
和耗时。独立索引服务的采用本身不应被直接视为创新点，也不能仅凭与
原 Retina 路径比较就宣称优于业界方案。研究贡献需由正确性契约、增量
表示与有界合并设计，以及外部对比和消融实验共同支撑。文献综述仍需补充
Pixels 正式论文及最新相关工作，避免未检索充分即断言存在研究空白。

## 四、研究目标

### 4.1 总体目标

在 Pixels + Trino 体系内实现一套面向数据打标的 SQL 行级 INSERT/UPDATE
机制：UPDATE 不直接改写列存文件，而将标签映射持久化到 RocksDB Tag
Index；打标完成后通过异步 Compaction 物化为新文件并修正主索引；系统在
百万行规模下具备可接受的端到端吞吐、正确的多列标签语义和可验证的重启
恢复能力，并为千万至亿级规模给出瓶颈分析与优化路径。

### 4.2 具体目标

1. 在 Trino Connector 中实现 INSERT/UPDATE 的完整 SPI 链路，支持精确
   主键更新（exact path，单次批量索引请求）与非精确谓词的 merge 兜底
   路径，并提供路由可观测性；
2. 设计并实现按列隔离的 Tag Index 存储结构，保证多标签列更新互不污染，
   正确处理 varchar、decimal 等类型的编码与精度；
3. 实现标签感知的 Compaction，将索引变更重写到物理文件，批量修正主索引，
   研究历史标签清理、重复主键解析消除及有界内存的增量消费方式；
4. 保证 INSERT 行号区间（row-id hull）随元数据持久化发布，修复检查点
   同路径重发等恢复缺陷，使已提交数据经进程重启后可正确恢复；
5. 建立 68 列打标 schema 的分级 benchmark（1M、10M、100M、1B），
   区分实际数据规模与每条语句更新规模，测量 SQL 提交、结果可见及完整
   周期成本，并与同版本 Trino 下的外部基线和原 Retina 路径比较。

### 4.3 需求边界与性能目标定义

原始会议确定的主线为：Worker 直接写入 INSERT 文件、RocksDB 记录标签
映射、打标结束后统一 Compaction。会议没有给出“百万行/秒”验收指标，
也未限定只更新少数列、只使用连续主键或固定打标轮数。DELETE 在原始
实施计划中明确不属于首期里程碑，本报告的实现范围为 INSERT 与标签
UPDATE，不能据此宣称完整支持所有 SQL DML。

| 指标 | 定义与边界 |
| --- | --- |
| 单语句处理规模 | 一条 UPDATE 能正确处理的实际匹配行数；与行/秒不同 |
| SQL 提交吞吐 | 实际成功行更新次数除以客户端提交到收到成功响应的时间 |
| 结果可见延迟 | 从开始打标到目标查询能读取正确最终结果的时间，包含本方案必要的 Compaction |
| 完整打标周期 | 规定的多条 UPDATE、最终物化及必要发布的总耗时，报告累计更新次数和唯一行数 |
| 内部阶段性能 | 编码、RPC、存储等计时，仅用于解释瓶颈，不替代 SQL 或业务完成时间 |

“接近百万行/秒”保留为待探索的 SQL 提交性能目标，不作为已确定的业务
及格线。实际时间预算与负载应由课题验收要求确认。研究假设是：在一定
更新列数和打标轮数下，独立标签记录可降低写放大和周期成本；实验也应
允许该假设在高列数、随机键或多轮覆盖场景下不成立。

## 五、研究内容

### 5.1 总体架构：写入路径与物化路径分离

系统划分为两条时序解耦的路径。写入路径上，Trino 接收 SQL DML，
Connector 在 Worker 内为 INSERT 直接创建 Pixels Writer 写文件，为
UPDATE 构造标签到主键集合的映射，经 gRPC 批量写入 IndexServer 的
RocksDB Tag Index。物化路径上，打标结束后由 CLI/RPC 触发 Compaction，
读取标签索引与原文件，重写出新的列存文件，并同步修正主索引与标签索引，
最终发布元数据与可见性。当前标签 SQL 查询通过主索引解析物理位置、
生成文件 split 并读文件完成过滤，属于索引辅助文件裁剪，尚非无需回表。
仅返回主键/标签的索引覆盖查询与返回任意基础列的完整行查询，应分别定义
和验证。表扫描消费 Compaction 后的新文件。INSERT 绕过 Retina 的整行
回放路径，但元数据发布和文件可见性仍调用既有服务，不能表述为完全移除
Retina 依赖。

### 5.2 UPDATE 双路由与谓词下推

当 UPDATE 谓词可归约为有限主键域时走 exact 路径：规划阶段提取主键域，
执行阶段以批量 Tag Index RPC 完成标签记录；否则回退到
beginMerge/PixelsMergeSink 的按页处理路径，按批刷新标签。通过路由日志
与分段指标（路由判定、RPC 次数、请求字节数、编码耗时）确保真实 SQL
的路径可审计，避免“以为走了批量、实际走了逐行合并”的测量错误。

当前 exact 路径主要覆盖常量赋值、有限主键域，存在 1,000,000 个候选键
上限。执行器直接枚举候选键并返回其数量，尚未在该路径确认键实际存在；
候选数量不一定等于匹配行数。需增加缺键、稀疏键、复合键组合缺失、空
结果及后续 INSERT 的测试，并研究批量存在性过滤或可信集合表示。
时间/维度谓词和非恒定表达式应按实际支持范围检查并测量，不能用 exact
路径数据代表所有 UPDATE。首次实现优先保证匹配集合和覆盖语义正确。

### 5.3 按列隔离的 Tag Index 设计

在索引协议（proto）与 RocksDB 逻辑键中引入列身份（columnName），以
“标记位 + 列名长度 + 列名 + 标签值”的编码方式为不同标签列维护独立
命名空间，同时保留旧的无列名条目以兼容历史数据。针对 decimal 类型，
在 Trino 侧将原生未缩放常量规范化为标准 SQL 小数字符串，防止标签值
在 Compaction 回写时被重复乘以列精度。

共享主键 RPC 将同一语句的主键集合传输一次并附带多个列/标签值，减少
按列重复序列化；服务端仍展开为逐列 VersionedUpdate，存储仍保留逐列
主键集合，尚未消除所有随列数增长的成本。需验证同一主键不同列互不
污染、同列多轮更新最新值正确、重复提交与历史版本回收的边界。

### 5.4 标签感知 Compaction 与主索引协同

Compaction 为所有重写行构造主键，批量调用主键解析与批量写入接口修正
主索引；标签索引解析共享同一快照，每个合并任务只保留自身源行的
relocation 映射，避免复制全量映射；Compaction 写入器先关闭再读取行组
数，保证发布的元数据行组计数与 row-id 区间正确。

现有 streaming RPC 先调用 Tag Index 的全量 entries()，客户端再聚合
完整逻辑列表，Compaction 随后构造全局快照。传输分块解决了单消息限制，
不代表存储遍历或内存处理已实现有界流式执行。后续重点研究按文件或键
分区消费增量、分块集合与可恢复的分批发布，测量峰值内存和历史轮数的
影响；内部索引布局的重大调整需在形成具体设计后与课题负责人讨论。

### 5.5 INSERT 持久化与发布协议

将 INSERT fragment 版本化，携带 minRowId/maxRowId 行号区间，索引写入器
记录分配区间，元数据在 finishInsert 时持久化行号区间与文件 REGULAR
状态，再注册文件可见性；旧版本 fragment 保留保守解码。当前元数据更新
和可见性注册是分开的服务操作，尚不能宣称跨服务原子提交。需定义中途
失败时的状态、重试幂等性、补偿或清理策略，并通过故障注入验证最终
正确性。对 writer、primary-index RPC、main-index flush 分别埋点。

### 5.6 故障恢复

研究 Retina 检查点在进程重启、同一时间戳重复发布等场景下的正确性，
修复检查点 body 被错误清理导致悬空指针的问题，并以回归测试覆盖；
梳理重启后元数据文件生命周期状态（REGULAR/RETIRED）与可见性注册的
恢复流程，识别当前需要人工介入的环节并给出自动化方案。

### 5.7 性能评测与瓶颈优化

围绕 68 列打标 schema（1 个主键、1 个时间戳、6 个维度、30 组
tag_type/tag_para）构建分级 benchmark，独立计时 base load、在线
INSERT、exact UPDATE、Compaction、标签 SELECT、重启恢复六个阶段。
INSERT 的主要成本包括 vnode 初始化和稳态 primary-index 发布；UPDATE
的 warm 路径曾主要消耗在 Java 主键去重/分组，而最终 RocksDB.write()
只占较小部分。两者应独立定位，不能把 INSERT 的 128 个 primary RPC
解释套用到 exact UPDATE。预热降低首次使用延迟但不会消除初始化工作，
必须同时披露初始化总成本。优化优先级由完整周期证据确定，而非固定
承诺客户端并发、RocksDB 参数或某一种分组写入能带来提速。

### 5.8 增量表示与扩展性的研究假设

当前逐列主键列表的处理与存储成本随实际标记行数和更新列数增长，历史
版本还可能引入随轮数增长的遍历成本。例如现有 codec 对每个 8 字节键
记录 4 字节长度，百万行、60 列的完整映射仅键编码约 720 MB，尚不含
标签、对象和历史版本。这是表示层的估算，不能等同于实际磁盘测量。

拟比较当前列表与分块/压缩键集合、共享集合引用等候选表示，在连续键和
随机键下评估编码、查询、覆盖更新、清理与合并成本。范围或位图压缩必须
保留实际存在集合，不能将带孔洞的候选范围误当成实际数据。候选方案的
取舍由正确性测试和测量决定，不能提前写成已实现的贡献。

## 六、关键问题与难点

1. SQL 语义与路由：下推条件不足可能使未满足谓词或不存在的候选键进入
   索引；保守回退可能增加扫描成本。需要验证实际匹配行、恒定/非恒定
   赋值、主键修改限制、边界范围和 fallback 路径。
2. 多列标签正确性：多标签列共享单一命名空间会导致物化值互相污染，
   decimal 等类型在未缩放值与字符串规范形式之间的转换极易引入精度
   错误，需要协议、编码、回写三层协同修复。
3. 索引服务扩展性：当前部署的客户端 fan-out 实验出现退化，但这一结果
   不足以证明所有并发写入都无效。需区分初始化排队、Java 分配与索引
   写入成本，处理多列集合重复、全量快照和历史版本积累的问题。
4. Compaction 一致性与成本：合并过程同时改写物理文件、主索引、标签
   索引，任一环节的行组计数、行号区间或 relocation 映射错误都会造成
   重启后数据不可见；同时合并阶段的重复解析是百万行以上规模的主要
   成本之一。
5. 可恢复性：检查点指针与 body 文件的生命周期、元数据文件状态迁移
   需要在异常重启下保持闭合，不能依赖人工修复。

## 七、技术路线与实验方案

### 7.1 技术路线

采用“原型实现 — 埋点观测 — 受控实验 — 瓶颈定位 — 局部优化”的迭代
路线。保留会议明确的写入与物化分离主线，先定义并验证匹配行、标签
覆盖、发布失败和恢复契约，再开展表示层与合并算法优化。每个阶段以完整
日志、配置和分段指标为证据，无法复现的历史数据不纳入验收基线。

### 7.2 实验环境

使用隔离的单机验证运行时（独立 PIXELS_HOME、独立 Trino/Metadata/
IndexServer/Retina 端口），不影响既有部署；构建与运行严格区分 JDK
版本（Retina 侧 Java 11 兼容性已有修复记录）。数据生成器应输出 68 列
CSV，按加载器约定用 `\N` 表示 SQL NULL。现有 fixture 曾将空字符串与
NULL 混用，正式实验前需重新核验，而非假定已修复。保存输入校验和、
字段数、行数、标签 NULL 计数与生成参数。

### 7.3 数据集与规模阶梯

主数据集保持 68 列：id、cap_time、6 个维度及 30 对标签，初始只填前
8 列、60 个标签列为 SQL NULL。按 1M、10M、100M、1B 行逐级推进，
每一级完整通过功能验收后再扩大；1B 是测例规范的目标规模，尚非已证明
能力。明确基础表规模、更新行数及单语句候选上限的区别。
3 列窄表只用于解释行宽成本，不替代主测例的验收数据。

| 负载维度 | 计划取值与目的 |
| --- | --- |
| 更新列数 | 2、8、60 列，评估每语句列数增长的成本 |
| 更新比例 | 基础表的 1%、10%、100%，实际匹配行数由参考结果校验 |
| 主键分布 | 连续范围、随机集合、带孔洞/缺失键、空匹配 |
| 业务谓词 | 主键，以及时间/维度条件，记录 exact 或 fallback 的实际路由 |
| 打标过程 | 一次更新 60 列；30 次分别更新一对后统一合并；同列重复覆盖 |
| 查询校验 | 主键/标签结果、标签与时间复合谓词、全表行数及 NULL 状态 |

一次更新 60 列与分 30 次更新的对照使用相同输入和最终标签结果。同列
覆盖另外验证最后一次赋值及历史值消失。非恒定赋值按明确的支持契约
纳入测试，未支持的操作必须清楚拒绝，不能静默当作常量更新。

### 7.4 测量指标与对照实验

- 端到端指标：SQL 提交、结果可见、完整周期分别计时。SQL 提交时间
  排除 Compaction，结果可见和完整周期包含必要物化、提交与发布；
- 路径指标：路由判定结果、RPC 次数与请求体积、Tag Index 服务端
  decode/storage 分段耗时；
- 索引指标：single-point 与 main-index 写入耗时、vnode 初始化耗时、
  Tag Index 初始化与 Java 去重/分组/编码耗时；
- 对照组：exact 与 merge 路径、宽表与窄表、物理表对表 INSERT 与
  UNNEST 合成 INSERT、串行与客户端并发发布；
- 正确性与恢复：Compaction 后标签谓词行数校验、重启后 count/min/max
  与标签计数校验、同时间戳检查点重发回归测试。

同时报告实际增量写入字节数、峰值内存、CPU 和存储占用。写放大定义为
所测打标周期的物理写入字节数与明确编码口径的逻辑变更字节数之比；初始
加载单独统计，数据文件、索引、日志及合并写入都需说明是否包含。
累计行更新次数、唯一更新行数和列更新量分别披露，避免重复覆盖使分母
混淆。连续运行或多轮实验检查吞吐退化与待合并数据增长。

冷启动至少区分新表索引创建、进程重启后重新打开已有索引、同进程稳态
运行。预热时间与资源计入生命周期成本；各组固定数据与运行状态，至少
重复 3 次并报告统计量及波动，不用单次最好值代表总体表现。

### 7.5 验收规则

每次结果必须记录提交 ID、运行时路径、配置、精确 SQL 与完整日志；
区分协议 probe、组件测试、SQL 写入、物化后查询与重启恢复证据。
协议写入并读回键集合不等于表级 UPDATE 完成；失败后人工补写或修复的
运行应标记诊断实验，不得作为干净验收。主验收要求输入 NULL 语义正确、
实际匹配行数正确、多列与覆盖更新正确、完整查询结果一致、失败处理及
重启流程可重复。若依赖人工 markReady 或元数据修复，明确标为未闭环。

### 7.6 外部基线、内部基线与消融

| 对照 | 研究目的与条件 |
| --- | --- |
| Pixels + Trino 与 Iceberg + 同版本 Trino | 主要外部基线；固定硬件、存储、数据和 SQL，核验实际 Trino 466 connector 的写能力与表配置 |
| 新方案与原 Retina 整行回放 | 内部基线；比较相同逻辑变更与最终结果的耗时和写入字节数，披露 API 与执行路径差异 |
| 新方案内部消融 | 比较重复/共享主键协议、旧/新去重路径、旧/新快照复制及未来合并算法 |
| Hudi + Spark/Flink | 可选扩展；作为整套系统比较，结果不直接归因于格式或索引算法 |

Trino 当前官方 Hudi connector 文档提供读访问，因此不能假定可与 Pixels
在同一 Trino 下执行同样写入。Iceberg 当前文档提供 DML，但仍须核验
部署版本，不能将最新文档能力直接套到 Trino 466。

外部比较采用相同的逻辑最终结果和目标查询。若对方提交后已可查询新值，
其可见性计时到此结束，不强制附加 optimize；本方案普通扫描所需的
Compaction 则必须计入。双方维护成本另行测量；若比较优化后的列存扫描，
统一布局目标并披露达到该目标的成本。记录文件大小、分区、压缩、排序、
索引和删除/更新模式。更强事务语义的代价不能全被归为算法效率差异。

### 7.7 学术评测依据与归因边界

参考 SIGMOD 2024 的 LST-Bench，将变更、查询和合并维护组成阶段，并
评估多轮运行的退化。Paimon 官方集群 benchmark 将持续写入吞吐与基于
检查点的数据新鲜度分别报告，可借鉴其持续运行及读回验证方式。
公开系统吞吐取决于硬件、既有表规模、变更分布和完成语义，不能将百万
行/秒作为行业统一标准。外部比较回答适用性，消融回答具体改动的贡献。

## 附录：需求、测例与技术路线核对结论

本次核对不改变会议约定的“直接 INSERT、独立标签记录、结束后统一
Compaction”主线，修订的是功能边界、扩展实现和实验论证。当前方案的
重点风险是 SQL 匹配集合、覆盖查询、跨服务发布、全量快照及历史版本
累积；单纯增加消息上限、客户端线程或报告 warm 内部吞吐不能解决它们。

| 核对项 | 来源与当前判断 | 报告处理 |
| --- | --- | --- |
| 宽表标签赋值、结束后查询 | 会议与 68 列规范一致 | 保留为明确业务约束 |
| 仅少列、多轮、连续主键 | 不是会议量化要求；只是部分现有实验形态 | 改为实验变量，纳入全 60 列及随机/缺键测试 |
| 点查无需回表 | 会议提出；当前 SQL 点查仍定位并读取文件 | 区分索引覆盖与完整行查询，标为待验证能力 |
| INSERT 完全绕过 Retina、跨服务原子发布 | 数据回放绕过，文件可见性仍依赖服务；操作分步执行 | 修正既有表述，补充失败和恢复契约 |
| 已达百万吞吐 | 候选键规模、内部计时与 SQL/周期口径曾混用 | 分别定义，并限定已有结果的证据边界 |
| 1B 可扩展、有界 streaming | 目标规模尚未验收；两端仍存在全量聚合 | 研究分块表示、分区消费与峰值内存 |
| 比较是否充分 | 当前主要是内部与局部实验 | 增加同版本 Trino + Iceberg、Retina 和消融 |

原始测例生成器及远程 CSV 的全面核验仍待进行，本报告对测例的判断以
仓库规范和记录为限。修订后的研究计划不预设外部比较结果或所有场景下
均有性能优势，最终结论由可复现实验给出。
