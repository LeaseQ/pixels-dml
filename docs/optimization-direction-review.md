## 1. 核心判断

“先记录标签变更、全部打标完成后统一合并”符合原始会议给定的延后查询条件，
值得继续验证。但现有索引布局、Compaction 实现和整体性能优势尚未得到充分证明。
不能把“方案有业务依据”写成“已经证明方向正确”，也不能把局部吞吐提升写成
完整打标流程已经达到目标。

INSERT直写与UPDATE延迟合并并列评估。先固定正常运行正确性及双路径总体对照，
暂缓新增微优化；根据端到端成本再决定导入、增量写入或物化的优化重点。若需更换主要索引表示或写入架构，先与
项目负责人讨论，不能仅凭本文直接实施。

## 2. 会议要求与实验假设的边界

根据用户提供的原始会议记录，明确约束包括：

- Trino 接入 SQL INSERT/UPDATE；INSERT 在 Worker 中使用 Pixels Writer 直接写文件，
  避免 Retina 整行回放。这不等于实现必须脱离全部 Retina 服务。
- UPDATE 将标签值到主键的映射记录在 RocksDB 中，不原地修改底层文件。
- 打标期间不查询，全部完成后通过 CLI/RPC Compaction 重写并整合数据。
- 严格在线ACID要求宽松，正常运行最终值与匹配行数必须正确；持久化配置披露，
  故障恢复与故障注入不作为本阶段新增目标或性能门槛。
- 会议提出了索引点查和合并后表扫描；“无需回表”的查询范围仍需明确并验证。

会议没有把百万行/秒、每次只改两列、固定多轮或连续且全部存在的主键范围确定为
业务前提。68 列测例中的更新列数、轮数、分布与规模都应成为实验变量。
不得只保留对当前快路径有利的测试。

需要检验的核心假设是：多轮打标避免重复处理所节省的成本，大于新增标签索引、
主键解析、最终重写和发布的成本。原始设计本身不能证明这个假设成立。

## 3. 已有证据与解释范围

以下记录均固定到 [Pixels 实验记录基线][experiments]，不混用不同实验的计时口径。
原记录个别小节出现晚于本次核对日期的标题或产物日期；本文按提交快照和实验条件
引用，未独立核验原始日志时间，后续正式报告需统一校准。

| 实验 | 记录结果 | 可以支持的判断 | 不足以支持的判断 |
| --- | --- | --- | --- |
| 1300 万行目标表，100 万行、两列、精确主键 UPDATE | SQL wall 1.997 秒、1.308 秒，约 50.1 万、76.3 万行/秒 | 特定暖态快路径已经取得局部改善 | 任意谓词、60 列、多轮或冷启动都达到此水平 |
| 固定 68 列源、带索引目标，100 万行 INSERT | 32 writers 的 Trino timeline 为 3.257 秒、暖态重复 3.375 秒，约 30 万行/秒 | 对应配置下并行写入有效 | 客户端总时间等于 timeline；完整流程达到百万吞吐 |
| 1100 万行表更新 100 万行后合并 | UPDATE 3.091 秒，COMPACT 316.312 秒；记录有最终行数、标签值校验 | 标签可合入文件；该实验合并成本占主要部分 | 一次成功证明所有规模、重启和异常路径正确 |
| 独立的干净 100 万行两标签流程 | UPDATE 4.598 秒，COMPACT 55.897 秒 | 小规模也存在明显物化成本 | 与上行构成严格同配置的线性扩展实验 |
| 最新 fresh INSERT 的 RocksDB 日志 | write stall 为零，pending compaction bytes 为零，累计 compaction 工作接近零 | 这组负载不支持后台 flush/compaction 堵塞为主要解释 | 排除 RocksDB 原生写队列、锁、分配或其他串行成本 |

1100 万行实验中，UPDATE 与 COMPACT 顺序耗时合计约 319.403 秒。如果只把 UPDATE
从 3.091 秒缩短到 1 秒，其他工作不变，总时间仅减少约 0.65%。这是该次实验的
成本推算，不是新压测，也不能用来否定多轮打标后只合并一次可能产生的摊薄收益。

## 4. 当前最重要的实现疑点

### 4.1 精确主键快路径必须验证实际存在性

[PixelsUpdateExecutor][update-executor] 将谓词编码为候选主键，调用
`appendShared` 后以 `primaryKeys.size()` 返回更新行数。该执行路径没有验证
候选键是否存在；主键互不重复与主键实际存在是两个不同条件。

最小回归例：表内只有 `id=1,3`，执行 `WHERE id BETWEEN 1 AND 3`。
预期仅两行受影响，不能为不存在的 `id=2` 留下会影响后续插入的标签。
当前代码提示存在性与计数风险，需要真实 SQL、索引内容及后续插入一起确认。
在问题解决或快路径适用条件得到严格证明前，连续主键测试速度不能代表通用 UPDATE。

### 4.2 合并成本可能随全表而非修改量增长

1100 万行实验只修改 100 万行，但重写、主键解析和 relocation 都涉及 1100 万行。
记录中解析约 150.643 秒，发布约 98.769 秒。分阶段时间可能嵌套、重叠，不能
直接相加；不过它们已经足以说明应优先分析合并的访问范围和关键路径。

需验证能否限制到受影响的文件或分区，以及随机稀疏更新是否实际上触及多数文件。
不能仅由“更新行数少”推断“需要重写的文件少”。

### 4.3 RPC 流式传输尚不等于端到端内存有界

[服务端 streamTagIndexEntries][stream-server] 先调用 `tagIndex.entries()`；
[PixelsTagIndex.entries][tag-entries] 构造全局主键与列的最新值映射；
[客户端收集函数][stream-client] 又汇总为列表。因此，分块传输解决单消息大小限制，
并未自动解决索引扫描、对象数量和全量物化的扩展风险。

若大规模实验确认内存或全局解析占主导，可讨论按文件/分区消费、批量解析和减少
中间物化。涉及改变主要索引组织时，须另行评审，不预先宣称这是已验证的最优方案。

### 4.4 调参需要由测量支持

已有多组增加 writers、flush 并行度或后台 flush 线程的实验被否决。
下一步应测量 grouped 请求解码、对象分配、原生写队列/锁、Trino 调度与 finishing
分别贡献多少延迟。不能因为没有 write stall 就断言 RocksDB 没有瓶颈，
也不能因为线程没有占满整台机器就直接归因于并行度不足。

## 5. 统一性能口径

- **单条 SQL 吞吐**：实际修改行数 / 客户端提交至成功完成的 wall time。
  INSERT 的源数据读取与生成成本须明确；Trino timeline 单独列示。
- **Connector/RPC 速率**：对应阶段处理量 / 该阶段耗时，只用于定位瓶颈。
- **打标至可查询总时间**：首条打标 SQL 开始，到全部打标完成且最终结果达到约定
  查询可见状态。包含必要合并与发布；预置数据构建和校验查询耗时分别报告。
- **完整导入与打标周期**：若比较包含 INSERT 的工作流，再单独计入导入耗时，
  不与已有基表上的打标流程混用。
- **重复打标工作量**：同时报告最终不同受影响行数、累计行更新次数、累计单元格
  赋值次数，不能把 30 轮重复更新同一批行称为处理了 30 倍不同数据行。
- **冷暖状态**：明确服务是否重启、索引/列族是否首次创建、是否复用 JVM 和缓存。
  冷启动单列，初始化成本完整披露；暖态不能仅取最好一轮。

顺序执行时可用 `T_tagging = Σ T_update + T_materialize` 作成本拆分；
有异步重叠时，以实际端到端时间为准，并记录重叠关系。
一条语句处理 100 万行与吞吐 100 万行/秒是不同指标。

## 6. 待执行的决定性实验

### A. 正确性先行

在小表和规模化测试中覆盖：不存在的主键、空匹配、随机键、同列多次覆盖、NULL、
decimal、非主键谓词及 fallback。核对受影响行数、最终逐键逐列值，并验证不存在键
上的 UPDATE 不污染后续 INSERT。count/min/max 校验不足以证明所有标签赋值正确。

核心流程为INSERT → UPDATE → COMPACT → 查询及位置核对，再正常运行第二周期。
不新增故障注入或恢复验收，已有重启记录保留为历史证据；披露持久化配置与限制。
UPDATE主实验限定主键筛选、常量赋值和独立多轮打标，其他路由仅核对能力边界。

### B. 验证延迟合并的价值

使用初始 60 个标签列均为 SQL NULL 的相同 68 列基表，每个实验臂从等价干净状态
开始，比较“一条语句更新 60 列”与“30 条语句各更新两列，最后合并一次”。
另加入同一列多轮覆盖以检验旧版本成本。各臂必须得到相同的最终值。

上述对照衡量轮次开销；另对相同的30条独立赋值语句比较逐轮物化与末尾物化，
才能隔离合并频率影响。不查询不等于后续UPDATE不依赖前次标签；依赖用例先验证
每条语句匹配集合、赋值和计数，不能用最终结果相同代替逐语句语义。

记录 SQL 累计时间、合并时间、发布时间、实际读写字节、峰值 RSS、GC 和最终文件
规模。物理写放大的分子应包括索引与文件等相关持久化写入，分母明确为逻辑变更
字节。优先比较总完成时间与字节量，避免因行更新次数不同而误读吞吐。

### C. 判断扩展性由什么决定

采用 100 万、1000 万和资源可承受的更大表规模，分别固定修改行数及修改比例。
每组同时覆盖聚集和随机分布，统计实际触及与实际重写的文件数、扫描/解析行数、
RPC 数、内存和总时间。先跑小规模确定成本，再扩大；十亿行仍是目标而非已有成果。

### D. 建立可比基线

- 内部基线：分别核对INSERT和UPDATE的原Retina路径及优化前版本。已核对的
  `TestRetinaService`更新负载删除旧键并插入新键，不可直接作为保留主键标签赋值
  基线；先固定输入和完成条件，可比性不成立时补适配或选合适对照，不硬凑加速比。
- 直接机制基线：开题前明确StarRocks列模式与Hudi MOR部分更新的选择依据和
  实验设计，开题后计划在目标平台跑通至少一个；核验实际更新路径、缺键和NULL
  语义，upsert不能直接当作UPDATE对照。
- 同引擎基线：保留同版本Trino上的Iceberg；确认Trino 466实际能力及生效配置，
  不把表格式通用COW/MOR配置当作Connector支持证明。本文未新增外部实测。
- 同一数据、硬件、存储条件与最终值，比较到达同等查询可见状态的总成本。
  披露事务隔离和持久性差异，不为对方强加本来不必执行的 optimize/compaction。
- 优先以 2/8/60 列、单轮/多轮、聚集/随机更新建立最小矩阵，再扩展维度。
- 主要对照拟在同一鲲鹏平台、统一资源预算下进行，先验证JDK、JNI/C++和外部
  系统兼容性。跨平台复现可选，不以硬件变化造成的绝对吞吐差证明方法优势。

所有性能臂至少重复三次，报告全部样本、中位数和波动；差异落在波动范围内时，
增加配对重复，不把微小变化宣布为收益。固定资源预算与合理配置，记录配置差异。
正式结果保留两个仓库 SHA、部署 jar 校验值、配置快照、数据种子/分布、SQL、query ID、
计时边界、正确性结果、原始日志与 profiler 产物，避免代码与运行包不一致。

## 7. 结果如何驱动下一步

| 验证结果 | 决策 |
| --- | --- |
| 正确性通过，多轮总时间和写入字节稳定优于基线 | 继续延迟合并路线，说明有收益的条件和交叉点 |
| 提交快，但总时间由全表解析/重写主导，且随表规模恶化 | 优先研究受影响文件/分区定位、批量解析与发布开销 |
| 内存随完整标签历史或主键列组合膨胀 | 讨论有界消费与索引表示调整，先给证据和设计再实施 |
| 优势只存在于连续主键、两列、暖态 | 收窄结论，补业务代表性测例，不能推广为通用 SQL UPDATE 优势 |
| 在预先确定的代表性负载上，全周期始终落后且无写放大/资源收益 | 重新评审索引布局或架构；保留否定结果，不继续靠挑选最好样本维持结论 |

开题准备优先级：研究问题与机制差异 → 具体方法假设 → 鲲鹏实验与外部基线设计。
近期先做双路径总体对照准备及正常运行验证，暂缓新增微优化。开题后在目标平台
推进外部基线验证与内部消融，再根据证据迭代方法并验证扩展性。外部验证不留到全部优化结束后，
但不是开题前的硬门槛；INSERT与UPDATE并列，不互相替代验收，允许收益不对称。

## 8. 与开题报告的关系

本文保留原评估快照，研究定位与[当前开题报告](thesis-proposal-20261123.md)及

过滤和并行本身不作为创新。需要证明方法差异及收益；正常运行语义修复属于
工程基础，适用边界属于实证贡献候选。详细依据及来源见开题报告第2、7章。

2026-11-24文献补核进一步明确：PDT、Fast Updates、L-Store及Mainlining已涉及
位置增量、值到行集合、累积更新或表示转换，不能将这些概念本身视作新方法。
主稿第3.4节已将候选研究拆为可证伪假设；本评估的历史性能快照不因此更新。

当前未完成上述验证，因此结论仍是：大框架有依据，整体性能优势未证实；
调整优化重点已有证据，是否更换架构尚待实验和讨论。
